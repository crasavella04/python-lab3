# Отладка

Ошибки, возникшие при создании и развёртывании сайта, в порядке появления: как проявлялась
проблема, в чём была причина и как её устранили.

## Окружение

### Системный Python устарел

**Симптом.** `python --version` → `Python 3.9.0`; `pip` и `pip3` привязаны к нему же.

**Причина.** На машине несколько интерпретаторов (3.7, 3.9, Miniconda), в `PATH` первым стоит 3.9.

**Решение.** Python 3.14 установлен через `uv python install 3.14` без изменения системного,
окружение создаётся явно под нужную версию: `virtualenv -p 3.14 .venv`.

### virtualenv отсутствует

**Симптом.** `python -m virtualenv` → `No module named virtualenv`.

**Решение.** `virtualenv` установлен как изолированная утилита: `uv tool install virtualenv`.
Ставить его через `pip` в интерпретатор, управляемый `uv`, нельзя: такой интерпретатор помечен как
*externally managed*.

### В «чистое» окружение попали чужие пакеты

**Симптом.** Сразу после `virtualenv -p 3.14 .venv` в выводе:

```text
added seed packages: babel==2.18.0, ..., mkdocs==1.6.1, ..., pip==26.2.1, ...
```

Ожидался только `pip`.

**Причина.** virtualenv кладёт в новое окружение пакеты из своего кэша (*app-data*), а кэш был
испорчен прошлыми запусками. Об этом же говорило предупреждение
`Could not migrate app data ... Cannot move a directory into itself`.

**Решение.** Окружение пересоздано со сбросом кэша:

```bash
virtualenv -p 3.14 --reset-app-data .venv
# added seed packages: pip==26.2.1
```

## Сборка

### `--strict` останавливает сборку на предупреждениях

Чтобы убедиться, что строгий режим действительно защищает публикацию, сайт был сломан намеренно:
в `index.md` добавлены ссылка на несуществующую страницу и ссылка на несуществующий якорь,
а в `docs/` — файл `draft.md`, не включённый в навигацию.

```text
WARNING -  The following pages exist in the docs directory, but are not included in the "nav" configuration:
  - draft.md
WARNING -  Doc file 'index.md' contains a link 'results.md', but the target is not found among documentation files.
WARNING -  Doc file 'index.md' contains a link 'about.md#net-takogo', but the doc 'about.md' does not contain an anchor '#net-takogo'.

Aborted with 3 warnings in strict mode!
```

Без `--strict` сборка завершилась бы успешно с битыми ссылками. Проверка якорей и страниц вне
навигации по умолчанию выключена и включена в `mkdocs.yml` в разделе `validation`.

### Предупреждение о MkDocs 2.0

**Симптом.** При каждой сборке Material for MkDocs выводит рамку с предупреждением: MkDocs 2.0
уберёт систему плагинов и тем, пути миграции нет.

**Решение.** Это предупреждение, а не ошибка, и `--strict` его не учитывает. Защита — точные версии
в `requirements.txt` (`mkdocs==1.6.1`, `mkdocs-material==9.7.7`): CI не подтянет несовместимую
версию.

### Нечитаемый вывод в консоли Windows

**Симптом.** При перенаправлении вывода `mkdocs` в конвейер кириллица в путях и символы рамки
превращаются в `C:\��\�����\...` и `\u2502`.

**Причина.** При выводе в конвейер Python на Windows кодирует текст в кодировке консоли (cp1251),
а не в UTF-8.

**Решение.** Запуск с `PYTHONUTF8=1` (или `PYTHONIOENCODING=utf-8`). На сборку это не влияет,
только на читаемость логов. В CI (Linux) проблемы нет.

### BOM в Markdown-файле

**Симптом.** После правки `about.md` командой PowerShell `Set-Content -Encoding utf8` файл начинался
с байтов `EF BB BF`.

**Причина.** Windows PowerShell 5.1 пишет UTF-8 с BOM.

**Решение.** BOM удалён (`sed -i '1s/^\xEF\xBB\xBF//'`). Текстовые файлы правятся редактором,
который пишет UTF-8 без BOM. Заодно добавлен `.gitattributes` с `eol=lf`: Git на Windows
предупреждал о замене LF на CRLF.

## CI/CD

### Задача висит в «Waiting for a runner»

**Симптом.** Первый запуск workflow больше 6 минут находился в статусе `queued`. В логе job'а:

```text
Job is about to start running on the hosted runner: GitHub Actions 1000000505
Waiting for a runner to pick up this job...
```

Второй запуск (следующий коммит) стоял в статусе `pending`.

**Причина.** Первый запуск не получил раннер на стороне GitHub. Второй ждал первого из-за
`concurrency` в workflow: одновременно разрешён только один деплой.

**Решение.** Старый запуск отменён вручную (*Cancel workflow run*), после чего новый сразу
стартовал и прошёл. Старый запуск всё равно был лишним: последний коммит содержит все изменения.

### Helios отвечает 500 на весь каталог

**Симптом.** Загрузка по SSH прошла, но шаг проверки упал. На любой адрес, включая статические
`.js` и шрифты, сервер отвечал:

```text
500 Internal Server Error
The server encountered an internal error or misconfiguration and was unable to complete your request.
```

**Причина.** Workflow клал в каталог сайта `.htaccess` с директивами `Options -Indexes` и
`ErrorDocument 404 ...`. Это нужно, чтобы Apache показывал страницу 404 темы. На Helios
переопределять такие директивы в `.htaccess` запрещено (`AllowOverride`), и Apache отвечает 500
на любой запрос в каталоге.

**Решение.** `.htaccess` больше не создаётся. Несуществующие страницы получают стандартный 404
сервера: код ответа правильный, но без оформления темы.

**Как нашли.** Ошибку поймал не браузер, а скрипт `scripts/check_site.py`, который запускается
в workflow после деплоя. Без него деплой выглядел бы успешным.

### Проверка падает при сборке не в тот каталог

**Симптом.** При локальной проверке сборки в подкаталоге `/~s000000/` скрипт проверки провалил
15 проверок из 17: все страницы отдавали 404.

**Причина.** Сайт был собран во временный каталог Git Bash (`$TMPDIR`), а HTTP-сервер был запущен
из другого каталога.

**Решение.** Сборка и сервер указывают на один явно заданный каталог. Заодно этот случай показал,
что скрипт проверки действительно ловит недоступный сайт, а не проходит всегда.

## Переход на Sphinx (P1)

### Плагин KaTeX тянет CDN

**Симптом.** Первая сборка упала: `Extension error (sphinxcontrib.katex) … katex.min.js does not exist`.

**Причина.** `sphinxcontrib-katex` копирует KaTeX из собственного пакета, а путь из настроек
приписывает к каталогу пакета, а не к `_static`. В исходниках обнаружилось и другое: по умолчанию
плагин несёт KaTeX 0.16.22, а **CSS и шрифты берёт с jsDelivr**. С ним сайт снова зависел бы от
CDN, от чего мы ушли в T4.

**Решение.** Плагин удалён. В `docs/conf.py` зарегистрирован свой рендерер `katex_local`. Он
использует штатную разметку формул из `sphinx.ext.mathjax`, но вместо MathJax подключает KaTeX 0.19
из `docs/_static/katex`.

### Формулы не отрисовываются, а скобки в тексте — отрисовываются

**Симптом.** Сборка с `-W` и все проверки `check_site.py` прошли. Но в браузере строчные формулы
на T2 остались сырым `\(\bar{x} \pm …\)`, а обычный текст «(версия 1.0, 500 значений)» KaTeX
отрисовал как формулу.

**Причина.** В `katex-init.js` разделители записались с одним обратным слешем: `"\("`. В JavaScript
это просто `"("`, поэтому KaTeX искал формулы между обычными круглыми скобками.

**Решение.** Разделители исправлены на `"\\("`. Ошибка не ловилась автоматически: разметка
формул в HTML была правильной, ломался только скрипт в браузере. Поэтому в `check_site.py`
добавлена проверка, что `katex-init.js` содержит правильные разделители. Заметить такую ошибку
можно было только глазами — аргумент за то, чтобы после изменений в шаблонах и скриптах
просматривать страницы с формулами в браузере.

### Якоря снова порядковые

**Симптом.** После переезда якоря разделов стали `#id1`, `#id2`, хотя на MkDocs они уже строились
из текста (T5). Внешние ссылки вида `…/t1/#методика` перестали бы работать.

**Причина.** Sphinx, как и docutils, выбрасывает из id не-ASCII символы и нумерует разделы.
`myst_heading_anchors` на id разделов не влияет: он нужен только для ссылок вида `[](#заголовок)`.

**Решение.** Преобразование `_unicode_section_ids` в `docs/conf.py` при чтении документа ставит
первым id раздела слаг из текста заголовка: `#методика`. Старый `idN` остаётся запасным, а явные
метки вроде `(strategy2)=` не трогаются. Адреса якорей совпали с теми, что были на MkDocs.

### Проверка ругается на ссылку лицензии

**Симптом.** После добавления метаданных (T5) `check_site.py` сообщил о внешних ресурсах
`http://purl.org/dc/elements/1.1/` и `https://creativecommons.org/licenses/by/4.0/`.

**Причина.** Проверка считала внешним ресурсом любой `<link>` с чужим адресом, кроме `canonical`.
Но `<link rel="license">` и `<link rel="schema.DC">` — метаданные, браузер их не загружает.

**Решение.** Учитываются только загружаемые ресурсы: `<script src>` и `<link>` с `rel` stylesheet,
preload, modulepreload или icon. Проверено, что внедрённый `<script src="https://evil.example/x.js">`
по-прежнему ловится.

## Итог

| Проблема | Где проявилась | Чем поймана |
|----------|----------------|-------------|
| Старый Python, нет virtualenv | локально | вывод команд |
| Лишние пакеты в окружении | локально | вывод `virtualenv` |
| Битые ссылки и якоря | сборка | `mkdocs build --strict`, затем `sphinx-build -W` |
| Кодировка, BOM, CRLF | локально | вывод команд, предупреждения Git |
| Раннер не взял задачу | GitHub Actions | статус запуска |
| `.htaccess` → 500 | Helios | `scripts/check_site.py` в CI |
| Плагин KaTeX с CDN по умолчанию | сборка | ошибка сборки, затем чтение исходников плагина |
| Неверные разделители KaTeX | браузер | **только визуальная проверка**; теперь — `check_site.py` |
| Порядковые якоря после переезда | сборка | проверка HTML после сборки |
| Ложное срабатывание на `rel="license"` | проверка сайта | `check_site.py` |
