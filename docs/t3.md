# T3. Отечественные CI/CD-сервисы и статические хостинги

Сравниваются три платформы CI/CD — **GitVerse**, **SourceCraft**, **GitFlic** — и шесть
вариантов размещения статического сайта. Отдельно разобрано, сколько стоит перенести на
отечественную платформу уже работающий workflow этого сайта.

## Методика и оговорки

- Платформы сравниваются **по официальной документации** на 10 октября 2026 года. Аккаунты на
  платформах для этой работы не создавались, поэтому всё, чего нет в документации, отмечено
  «не указано». Это тоже результат: для эксплуатации пробел в документации почти так же плох,
  как отсутствие функции.
- По **Helios ИТМО** данные получены из реального деплоя этого сайта (см. «Отладка»).
- Миграция оценивается на **настоящем** workflow
  [`.github/workflows/pages.yml`](https://github.com/crasavella04/python-lab3/blob/main/.github/workflows/pages.yml).
  Перенесённая на GitVerse версия лежит в
  [`research/t3/gitverse-pages.yml`](https://github.com/crasavella04/python-lab3/blob/main/research/t3/gitverse-pages.yml).
- Для сравнения в таблицах есть столбец **GitHub Actions**.

## Платформы CI/CD

| Критерий | GitVerse (СберТех) | SourceCraft (Яндекс) | GitFlic (Группа Астра) | GitHub Actions |
|---|---|---|---|---|
| **Раннеры** | облачные, пользовательские и организационные | облачные (4 vCPU, 8 ГБ RAM), serverless, self-hosted (в том числе в Kubernetes) | **только собственные агенты**: shell, PowerShell, Docker, Kubernetes (бета). Без агента конвейер не запускается | облачные (4 CPU, 16 ГБ) и self-hosted |
| **Синтаксис** | как у GitHub Actions: `on`, `jobs`, `steps`, `uses`, `run`; файлы в `.gitverse/workflows/`, **читает и `.github/workflows/`** | собственный: `workflows → tasks → cubes` в `.sourcecraft/ci.yaml` | как у GitLab CI: `stages`, `rules`, `needs`, `artifacts`, `include` в `gitflic-ci.yaml` | — |
| **Совместимость** | с GitHub Actions: контекст `github.*` поддерживается как синоним `gitverse.*`, есть `secrets.*`, `vars.*`, `workflow_call`, `container` | **запускает действия GitHub Actions** как кубики (`action: имя@версия`) и пайплайны GitLab (`gitlab_workflow`), только на облачных воркерах | с GitLab CI: синтаксис выбран для упрощения миграции с GitLab | — |
| **Каталог действий** | действия через `uses` (в документации — `actions/checkout@v4`), свои `gitverse/*` для Pages, репозиторий starter-workflows | действия из GitHub Marketplace; переиспользование кубиков через `uses` | шаблоны CI/CD и компоненты (`include: component`) | Marketplace |
| **Секреты** | на уровне репозитория и организации, `${{ secrets.X }}`, в логах маскируются | `${{ secrets.X }}`; доступ к Yandex Cloud через сервисные подключения и токены | переменные CI/CD, Vault и StarVault | репозиторий, окружение, организация; OIDC |
| **Артефакты** | 500 МБ на все репозитории, хранятся 30 дней | до 100 МБ на кубик, 10 ГБ на организацию, хранятся 14 дней | `artifacts` с `expire_in` (в том числе `never`) | 500 МБ (Free, приватные репозитории) |
| **Кэш** | есть, в лимит артефактов не входит; размер не указан | в найденной документации не описан | `cache` с `key` и `paths`, общий на репозиторий | 10 ГБ, удаление через 7 дней без обращений |
| **Бесплатный лимит** | 500 мин (приватные) / 1 000 мин (публичные); у верифицированных организаций 1 000 / 2 000 | Free: **1 000 мин/мес**; хранилище 2 ГБ; для образовательных и open-source проектов лимиты повышают по запросу | облачных минут нет: лимит — ресурсы вашего агента | публичные — бесплатно; приватные — 2 000 мин/мес |
| **Таймаут задачи** | облако: 15 мин по умолчанию, **максимум 30 мин**; собственные раннеры — 3 ч | кубик — 20 мин, задача — 60 мин | определяется вашим агентом | 6 ч |
| **Расписание** | облако: интервал не меньше 15 мин | — | планировщик конвейеров | не меньше 5 мин |
| **Свой статический хостинг** | **GitVerse Pages** | **SourceCraft Sites** | нет | GitHub Pages |
| **Документация** | на русском, но с пробелами: не описаны `permissions`, `concurrency`, характеристики облачных раннеров; в разделе матриц — заглушка «!TODO» | подробная, на русском и английском; часть страниц только на английском; в разных версиях страницы лимитов цифры расходились | синтаксис описан подробно; условия облака (агенты, тарифы) не описаны | эталон |

### Выводы по CI/CD

- **GitVerse** ближе всех к GitHub Actions. Он понимает тот же синтаксис и контекст `github.*`,
  умеет читать `.github/workflows/`, а у шагов деплоя Pages есть прямые аналоги. Главное
  ограничение — **30 минут на задачу** в облаке. Для сборки сайта этого хватает с запасом,
  для вычислений из T2 — нет.
- **SourceCraft** выделяется ресурсами и интеграцией с Yandex Cloud: задача до 60 минут,
  запуск действий из GitHub Marketplace без аккаунта GitHub. Но синтаксис у него собственный,
  и workflow придётся переписать по структуре, сохранив сами действия.
- **GitFlic** удобен тем, кто приходит с GitLab, но в облачной версии нужно поднимать и
  обслуживать собственного агента. Для студенческого проекта это самый затратный вариант.

## Варианты размещения

| Критерий | Helios ИТМО | Yandex Object Storage | Selectel S3 | Timeweb App Platform | GitVerse Pages | SourceCraft Sites |

## Миграция workflow с GitHub Actions

Workflow этого сайта: сборка MkDocs с `--strict` и проверкой манифеста T2, деплой на GitHub Pages
через официальную связку артефактов и деплой на Helios по SSH с проверкой после деплоя.

### На GitVerse — выбранная платформа

| Конструкция в `pages.yml` | На GitVerse | Категория |
|---|---|---|
| `on: push / pull_request / workflow_dispatch` | те же ключи | **без изменений** |
| `jobs`, `needs`, `if`, `runs-on`, `env`, `steps`, `run` | те же ключи | **без изменений** |
| `${{ vars.X }}`, `${{ secrets.X }}` | тот же синтаксис, переменные и секреты задаются в настройках репозитория | **без изменений** (перенести значения) |
| `github.event_name`, `github.sha` | `github.*` — синоним `gitverse.*` | **без изменений** |
| `actions/checkout` | используется в документации GitVerse (v4) | **без изменений** (сменить версию) |
| `pip install`, `mkdocs build --strict`, `provenance.py check`, деплой на Helios через `tar \| ssh` | обычные shell-команды | **без изменений** |
| `actions/setup-python@v6` с `cache: pip` | наличие в каталоге GitVerse не подтверждено → `container: python:3.14-slim` | **переписать** |
| переменная окружения `GITHUB_SHA`, на которую опирается `mkdocs.yml` | встроенные переменные не документированы → `GITHUB_SHA: ${{ github.sha }}` в `env` | **переписать** |
| `actions/upload-pages-artifact`, `actions/deploy-pages` | `gitverse/upload-pages-artifact@v1.0.0`, `gitverse/deploy-pages@v1.0.0`; источник Pages = Workflow | **переписать** (замена имени) |
| `SITE_URL` для GitHub Pages | `https://<владелец>.gitverse.site/python-lab3/` | **переписать** (значение) |
| `permissions: pages: write, id-token: write` (OIDC) | не документировано; деплой Pages обходится без него | **не поддерживается** — убрать |
| `concurrency: group: deploy-…` | не документировано | **не поддерживается** — убрать; параллельные деплои не исключены |
| `environment` с `url: ${{ steps.deployment.outputs.page_url }}` | `environment` с именем и URL есть, правила защиты не описаны | **частично** |
| Проверка сайта после деплоя Pages по `page_url` | выход `deploy-pages` не документирован → адрес из `vars.SITE_URL` | **переписать** |
| Задача дольше 30 минут | на облачном раннере невозможно | **не поддерживается**; для нас неактуально: сборка идёт 1–2 минуты |

**Итог по трудозатратам.** Построчное сравнение версий без комментариев и пустых строк: из 94
строк исходного workflow 36 перенесены дословно, 58 удалены или изменены, 24 добавлены. Цифра
изменений завышена: часть правок необязательна. Блок SSH упрощён (`ssh -i` вместо
`~/.ssh/config`), шаг проверки GitHub Pages после деплоя убран, `setup-python` в двух задачах
заменён одной строкой `container:`. Вынужденные правки — те, что в таблице отмечены «переписать»
и «не поддерживается»: имена двух действий Pages, `GITHUB_SHA`, адрес сайта, `permissions` и
`concurrency`. Вся логика сборки, проверок и деплоя на Helios переносится как есть. Оценка —
**около часа**, большая часть которого уйдёт на перенос переменных и секретов и на первый
пробный запуск.

### На SourceCraft

Структура переписывается целиком: `jobs/steps` превращаются в `workflows → tasks → cubes`.
Действия GitHub (`checkout`, `setup-python`) можно оставить как кубики `action:`, но только на
облачных воркерах. Shell-команды переносятся без изменений. Деплой на SourceCraft Sites устроен
иначе, чем на Pages: сайт публикуется из **ветки**, поэтому собранный `site/` нужно коммитить в
отдельную ветку (подход `gh-pages` из «О сайте») или в каталог, указанный в `sites.yaml`. Оценка —
**2–3 часа**.

### На GitFlic

Файл пишется заново в синтаксисе GitLab CI: `stages`, задачи верхнего уровня, `image`, `script`,
`rules`. Действий GitHub нет, поэтому `checkout` делает агент, а Python берётся из образа. Главная
работа — **поднять собственного агента** (ВМ или Docker с `java -jar runner.jar`) и
обслуживать его. Встроенного хостинга нет, деплой только на Helios или в S3 скриптом. Оценка —
**полдня и больше** плюс постоянные затраты на агента.

### Что не переносится нигде

- **OIDC-деплой на GitHub Pages** (`id-token: write`) — механизм самого GitHub.
- **Деплой на GitHub Pages** как таковой: на каждой платформе свой хостинг или внешний.
- **Действия, которые обращаются к API GitHub** (комментарии к PR, релизы GitHub). Такие действия
  у нас не используются.

## Вывод

Для этого сайта оптимальная пара — **GitVerse + GitVerse Pages**, с Helios как вторым адресом.
Workflow переносится почти дословно, хостинг бесплатный и с HTTPS, связка
`upload-pages-artifact` + `deploy-pages` повторяет официальный подход GitHub. Ограничение
в 30 минут на задачу для сборки сайта несущественно.

Выбор меняется в трёх случаях:
1. **Нужны тяжёлые вычисления в CI или интеграция с Yandex Cloud** — выбирать **SourceCraft**:
   задача до 60 минут, serverless-воркеры, сервисные подключения к облаку.
2. **Команда уже работает с GitLab CI или нужен on-premise** — выбирать **GitFlic** с собственными
   агентами, а сайт размещать в Object Storage или на Helios.
3. **Нужен свой домен с HTTPS** — для GitVerse Pages и SourceCraft Sites эта возможность не
   документирована. Тогда сайт выкладывают в **Yandex Object Storage** (бесплатного уровня
   хватает с большим запасом) или на **Selectel** с CDN, а CI с любой из платформ загружает его
   через S3 API.
