# P4. Развёртывание на Helios с контролем качества доставки

До P4 выкладка на Helios была одной командой: удалить каталог сайта и распаковать в него
новый архив. Эта схема работала, но у неё четыре недостатка:
- при обрыве посередине сайт оставался пустым или неполным;
- прежняя версия не сохранялась;
- опубликовать можно было только `main`;
- «успех» означал лишь, что команда не упала, а не что сайт работает.

В P4 всё это исправлено. Вся работа проверена на настоящем Helios серией специально сломанных
выкладок.

| Что | Где |
|---|---|
| Скрипт выкладки на сервере | [`scripts/helios_deploy.sh`](https://github.com/crasavella04/python-lab3/blob/main/scripts/helios_deploy.sh) |
| Выкладка, healthcheck, автооткат | job `deploy-helios` в [`.github/workflows/pages.yml`](https://github.com/crasavella04/python-lab3/blob/main/.github/workflows/pages.yml) |
| Ручной откат, удаление preview | [`.github/workflows/helios-admin.yml`](https://github.com/crasavella04/python-lab3/blob/main/.github/workflows/helios-admin.yml) |
| Настройка SSH (общая часть) | [`.github/actions/helios-ssh`](https://github.com/crasavella04/python-lab3/blob/main/.github/actions/helios-ssh/action.yml) |
| Замеры по истории запусков | [`research/p4/timings.py`](https://github.com/crasavella04/python-lab3/blob/main/research/p4/timings.py) |

## Схема выкладки

**Отдельный ключ деплоя.** CI входит на Helios по ключу, созданному только для выкладки, а не по
личному ключу или паролю. Приватная часть хранится в секрете `HELIOS_SSH_KEY` и в репозиторий не
попадает. Ключ хоста закреплён в `.github/known_hosts`, с `StrictHostKeyChecking yes` (T4).

Скрипт выкладки готов к работе как forced command этого ключа: команду он берёт из
`$SSH_ORIGINAL_COMMAND` и понимает только `deploy`, `rollback`, `remove` и `list`. Пока forced
command на сервере не включён, CI перед выкладкой копирует скрипт на Helios сам. После включения
достаточно задать переменную `HELIOS_FORCED_COMMAND=true`.

**Раскладка на сервере:**

```text
~/public_html/python-lab3/                    ← рабочая версия main (корень сайта)
~/public_html/python-lab3/preview/<ветка>/    ← рабочие версии остальных веток
~/.deploy/python-lab3/releases/<слот>/<релиз>/ ← предыдущие версии, по 3 на слот, вне веб-доступа
~/.deploy/python-lab3/stage/<pid>/            ← приём архива
```

Релиз называется по времени выкладки и коммиту, например `20261010T212853Z-ca54546`. В каждую
версию сайта скрипт кладёт `release.json` с именем релиза, коммитом и временем. По этому файлу
видно, что сейчас опубликовано, например
<https://se.ifmo.ru/~s564180/python-lab3/release.json>.

**Шаги одной выкладки:**

1. CI собирает сайт, упаковывает в `tar.gz` (1,5 МБ) и передаёт по `ssh` в stdin скрипта.
2. Скрипт распаковывает архив в `stage/<pid>`, рабочая версия при этом не затрагивается.
3. Проверки: в архиве есть `index.html`, нет символических ссылок и каталога `preview/`, размер
   не больше 100 МБ.
4. Блокировка через `mkdir lock`: этот вызов атомарен, а `flock` есть не на всех системах. Корень
   и preview лежат в одном дереве, поэтому выкладки идут строго по очереди. В CI то же самое
   обеспечивает `concurrency: helios`.
5. Переключение двумя переименованиями: рабочая версия уходит в `releases/`, новая встаёт на её
   место. У корня перед этим каталог `preview/` переносится в новую версию.
6. Из `releases/` удаляются версии сверх трёх последних.

`rsync` здесь не нужен. Он обновляет файлы на месте, и во время передачи сайт состоит из смеси
старых и новых файлов. Релизам нужна полная копия, а для сайта в 1,5 МБ архив по `ssh` занимает
3–5 секунд. Для большого сайта подошёл бы `rsync --link-dest` в каталог нового релиза: неизменные
файлы стали бы жёсткими ссылками на предыдущий релиз, а переключение осталось бы тем же.

## Preview веток

Ветка `main` публикуется в корень. Любая другая ветка публикуется в `preview/<имя>/`, где имя
получено из названия ветки: `feature/New_X` → `feature-new-x`. Сборка для preview отличается
тремя вещами:

- `SITE_URL` указывает на подкаталог, поэтому ссылки, `sitemap.xml` и канонические адреса
  ведут на preview, а не на основной сайт;
- на каждой странице есть `<meta name="robots" content="noindex, nofollow">`, чтобы поисковики не
  индексировали черновики;
- сверху плашка «Предварительная версия ветки … Опубликованный сайт — в корне» (параметр
  `announcement` темы Furo).

Выкладка корня не трогает preview: каталог `preview/` переносится в новую версию корня. Откат
корня тоже. Когда ветку удаляют, событие `delete` запускает `helios-admin.yml`, и preview удаляется
вместе с сохранёнными релизами.

На GitHub Pages так нельзя: у репозитория один сайт Pages, и опубликовать вторую ветку рядом
некуда. Preview там бывают только для pull request при особой настройке. Поэтому `build-pages`
работает только для `main` и pull request, а ветки публикуются только на Helios.


## Healthcheck

Сразу после переключения шаг `Healthcheck` запускает `scripts/check_site.py` для опубликованного
адреса:
- **код ответа 200** на всех страницах и ресурсах;
- **контрольная строка** `<meta name="build-marker" content="python-lab3:<коммит>:<площадка>">`,
  в которой коммит должен совпасть с коммитом этой сборки;
- поиск, формулы, отсутствие внешних CDN (из прошлых этапов).

Если что-то не совпало, скрипт завершается с кодом 1 и job падает. Каждая проваленная проверка
выводится аннотацией `::error`, поэтому причина видна на странице запуска без чтения лога.

Проверка контрольной строки ловит не только поломку, но и «тихую» ошибку: когда сайт работает,
но выкачен не тот коммит. Например, если переключение не произошло, а старая версия отвечает 200.

## Откат

**Автоматический.** Если healthcheck не прошёл, следующий шаг выполняет
`rollback <цель> failed`. Сломанная версия уходит в `releases/` под именем `<релиз>-failed`,
чтобы её можно было разобрать, а на её место возвращается предыдущий релиз. Затем healthcheck
запускается снова, уже с коммитом восстановленной версии. Job всё равно остаётся красным: выкладка
не удалась, и об этом должны узнать.

**Ручной.** Два способа:

- *Actions → Helios rollback and cleanup → Run workflow*: `action=rollback`, `target=root` или
  `preview/<имя>`, релиз можно не указывать;
- тег: `git tag rollback/root/<любое> && git push origin rollback/root/<любое>`.
  Тег навсегда остаётся в истории как запись о том, кто и когда откатил.

Без имени релиза выбирается ближайший релиз старше текущего. Версии с пометкой `-failed`
пропускаются. Повторный откат уходит ещё на шаг назад. Вернуться вперёд можно, указав имя релиза
(список даёт `action=list`) или выложив новый коммит. После ручного отката тоже запускается
healthcheck с коммитом восстановленной версии.

Откат — те же два переименования, что и выкладка. Файлы не копируются, поэтому откат занимает
доли секунды, а job целиком — около (уточняется) с, из них основное время уходит на подготовку
раннера и healthcheck.

`[p4-fault: interrupt]` обрывает передачу на середине. В `main` метки не действуют.

## Обрыв выкладки на середине

### Helios

Что происходит, зависит от момента обрыва.

| Момент обрыва | Что видит читатель | Что остаётся на сервере |
|---|---|---|
| во время передачи архива | прежнюю версию, без перерыва | ничего: `tar` получает неполный архив, скрипт удаляет `stage` |
| во время проверок архива | прежнюю версию | ничего, как выше |
| между двумя переименованиями | на доли миллисекунды 404 | ничего: сигналы на это время игнорируются |
| `kill -9` или перезагрузка между переименованиями | 404 до следующей выкладки или отката | прежняя версия в `releases/`, `stage` уберёт следующая выкладка |
| после переключения, до конца healthcheck | **новую, ещё не проверенную** версию | если job оборвался, автооткат не сработает |

Первые две строки проверены на Helios: передачу обрывали на середине (коммиты D и F).
Рабочая версия не изменилась, и шаг «Live version after interrupted upload» это подтвердил.

Нашлась и настоящая ошибка. После обрыва D временный каталог остался на сервере, и его убрала
только следующая выкладка. Причина — SIGPIPE: при оборванном соединении stderr скрипта ведёт в
закрытый сокет, и первая запись туда убивала процесс раньше очистки (подробно — в
[«Отладке»](debugging.md)). После исправления повторный обрыв F мусора не оставил.

Самое слабое место схемы — последняя строка. Healthcheck идёт **после** переключения, поэтому
сломанная версия какое-то время видна. В демонстрации C это около 40 секунд: столько идёт
проверка с раннера GitHub до Helios плюс откат. Убрать это окно можно по схеме blue-green: сначала
выкладывать в скрытый каталог, проверять его по отдельному адресу и только потом переключать. Цена
— ещё одна полная проверка на каждую выкладку. Для учебного сайта окно в 40 секунд допустимо.

### GitHub Pages

Здесь выкладка устроена иначе:
- сборка загружается артефактом (`upload-pages-artifact`, хранится 1 день);
- `deploy-pages` просит GitHub опубликовать этот артефакт и ждёт результата;
- переключение делает сам GitHub, атомарно, на своей стороне.

Оборвать выкладку «на середине» с нашей стороны нельзя: файлы на хостинг не передаются по одному.
Если job отменят, пока `deploy-pages` ждёт, действие перехватывает SIGINT/SIGTERM и отменяет
выкладку (`process.on('SIGTERM', cancelHandler)` в его исходниках). Сайт остаётся прежним.
Обратная сторона: если GitHub не довёл выкладку до конца, повлиять на это нельзя, остаётся
ждать или перезапустить.

Отката как отдельной функции на Pages нет. Вернуть версию можно двумя способами:
- перезапустить старый запуск (*Re-run jobs*), но только пока жив его артефакт, то есть сутки;
- сделать `git revert` и пройти полный цикл сборки.

## Сравнение GitHub Pages и Helios

Цифры — по всем запускам из push в `main` за время работы (`research/p4/timings.py`, публичный
API GitHub):

(уточняется)

| | GitHub Pages | Helios |
|---|---|---|
| Время доставки | (уточняется) | (уточняется) |
| Надёжность | (уточняется) | (уточняется) |
| Атомарность | на стороне GitHub, из коробки | своя: stage + переименования, проверена обрывами |
| Кэш у читателя | `Cache-Control: max-age=600`: после выкладки браузер до 10 минут может показывать старые файлы (P3) | nginx без `Cache-Control`, браузер решает сам по `Last-Modified` |
| Preview веток | нет: один сайт на репозиторий | есть: `preview/<ветка>/` |
| Откат | перезапуск старого запуска (артефакт живёт сутки) или `git revert` | `rollback`: доли секунды, три последних релиза на слот |
| Отладка | только логи Actions; на сервер не зайти, его журналов не видно | `ssh` на сервер: файлы, `release.json`, `list`, журнал скрипта в аннотациях |
| Обслуживание | нулевое | своя система: ключ, `known_hosts`, скрипт, квоты, блокировка |

**Итог.** GitHub Pages проще и надёжнее как сервис: атомарность, CDN и отсутствие обслуживания
даются бесплатно. Но сделать с ним можно только то, что он умеет сам. На Helios всё пришлось
построить самостоятельно, зато получилось больше: preview веток, мгновенный откат на любую из
трёх версий, полный доступ к серверу при отладке. Цена — 230 строк shell-скрипта и workflow,
которые тоже нужно было отлаживать, о чём говорит ошибка с SIGPIPE.
