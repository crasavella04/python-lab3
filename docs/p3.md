# P3. Воспроизводимый конвейер «данные → результат → сайт»

В T2 результаты считались отдельно и коммитились вместе с манифестом (стратегия 2). Здесь —
стратегия 1: **расчёт выполняется при каждой сборке сайта**. Чтобы неизменившиеся результаты
не пересчитывались, используется кэш по содержимому. Таблица и график ниже — не вставленные
вручную числа: они получены из исходных данных при сборке именно этой версии сайта.

## Как устроен конвейер

```text
research/p3/data/measurements.csv ─┐
research/p3/data/DATASET.json ─────┤  (паспорт: версия, SHA-256)
research/p3/pipeline.py ───────────┼─→ ключ кэша = SHA-256(данные + код + параметры)
                                   │
                ┌──────────────────┴─────────────────┐
         ключ есть в .cache/p3            ключа нет
         → копировать готовое             → расчёт (numpy, matplotlib) → сохранить в кэш
                └──────────────────┬─────────────────┘
                                   ▼
                     docs/p3/generated/: table.md, figure.svg, summary.csv, stats.json
                                   ▼
            sphinx-build: таблица и график вставляются в страницу,
            метка версии (коммит, дата, версия данных) подставляется в момент сборки
```

**Вызов из сборки.** Сайт собирается командой `nox -s site`, она запускает по очереди:
1. `research/p3/pipeline.py` — расчёт или кэш;
2. `sphinx-build -W` — строгая сборка;
3. проверку орфографии.

Так же собирает CI. Отдельно вызвать расчёт и забыть про сборку, или наоборот, нельзя.

**Кэш по содержимому.** Ключ — SHA-256 от трёх частей:
- файл данных;
- код расчёта;
- параметры (число бутстреп-выборок, уровень значимости, `seed`).

Если ключ совпал, готовые файлы просто копируются, а numpy и matplotlib даже не импортируются:
проверка кэша написана на стандартной библиотеке. Изменилось хоть что-то из трёх — ключ новый,
и результат считается заново. Устаревший результат из кэша получить нельзя.

Это отличие от кэша MyST-NB, разобранного в T2: там ключ — только код ячеек, и после изменения
данных кэш выдаёт старый результат. Хранятся пять последних результатов, поэтому возврат к
прошлой версии данных тоже берётся из кэша.

**Кэш в CI.** Каталог `.cache/p3` сохраняется между запусками действием `actions/cache`. Ключ
строится из хеша данных и кода, а `restore-keys` подхватывает кэш прошлого запуска, если ключ
новый:

```yaml
- uses: actions/cache@caa296126883cff596d87d8935842f9db880ef25 # v5.1.0
  with:
    path: .cache/p3
    key: p3-${{ hashFiles('research/p3/data/**', 'research/p3/pipeline.py') }}
    restore-keys: p3-
```

**Метка версии не кэшируется.** Коммит и дата сборки подставляются Sphinx в момент сборки
(`myst_substitutions` в `docs/conf.py`) и в файлы результата не попадают. Иначе каждый коммит,
даже правка опечатки в тексте, менял бы результат и сбрасывал кэш.

**Защита данных.** Паспорт `DATASET.json` хранит версию и SHA-256 файла. Если поменять CSV, не
выпустив новую версию, конвейер останавливается:
`P3: файл данных не совпадает с паспортом DATASET.json — данные изменили без новой версии`.
Версии данных воспроизводимы: `make_dataset.py 1.1` всегда даёт один и тот же файл.

## Кэш: замер выигрыша

Локально (Windows, Python 3.14):

| Запуск | Кэш | Время |
|---|---|---:|
| данные v1.0, первый запуск | промах: расчёт | 4,914 с |
| данные v1.0, повторно | попадание | 0,005 с |
| данные v1.1 | промах: новый ключ | 1,052 с |
| снова данные v1.0 | попадание: результат v1.0 остался в кэше | 0,005 с |

Первый расчёт дольше второго промаха (4,9 против 1,1 с): при первом запуске numpy и matplotlib
читаются с диска, а потом уже из файлового кэша ОС. Попадание в кэш в 200–1000 раз быстрее
расчёта: вся работа — посчитать хеши трёх файлов и скопировать четыре файла.
