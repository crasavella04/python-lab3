# T5. Публикуемость и цитируемость результата

Сайт с результатами становится публикацией, когда на него можно **сослаться** так, что ссылка
не сломается, **найти** его в научных поисковиках, **понять**, какая версия кода и данных
стоит за каждой цифрой, и **законно использовать** текст, код и данные. Ниже разобрано, что
для этого нужно, что из этого уже сделано на этом сайте и как с этим справляются генераторы
из T1 и хостинг Helios.

Поддержку механизмов в генераторах я проверял на тестовых сайтах из T1. Каждому проекту родными
средствами переданы одинаковые сведения — автор с ORCID, описание, адрес сайта, DOI, лицензия —
и проверено, что попало в HTML. ORCID в тесте — официальный тестовый идентификатор ORCID, DOI —
заведомо несуществующий.

## Постоянные ссылки и стабильность URL

**Адрес страницы** у всех четырёх генераторов по умолчанию выводится из имени файла:
`docs/t2/index.md` → `/t2/`. Переименовали файл — старая ссылка стала 404. Pelican здесь удобнее
остальных: адрес задаётся полем `Slug` в метаданных статьи и от имени файла не зависит.

**Якоря разделов** — проблема серьёзнее, чем кажется. Все четыре генератора по умолчанию
выбрасывают из кириллических заголовков буквы и строят **порядковые** якоря:

| Генератор | Якоря заголовков «Формулы», «Рисунок»… |
|---|---|
| MkDocs (Python-Markdown) | `#_1`, `#_2`, `#_3` |
| Sphinx + MyST | `#id2`, `#id3`, `#id4` |
| Pelican | `#_1`, `#_2`, `#_3` |
| Jupyter Book 2 | `#id`, `#id-1`, `#id-2` |

Добавили раздел в начало страницы — все якоря ниже сдвинулись, и ссылка «см. раздел
Замеры» из чужой статьи теперь ведёт в другой раздел. Без ошибки 404, поэтому этого никто не
заметит. На этом сайте до T5 было так же: в T1 были якоря `#_1` … `#_11`.

Что сделано:
- Якоря строятся из текста заголовка с сохранением кириллицы: `#методика`, `#замеры`, `#итоги`. При
  вставке разделов они не сдвигаются и меняются только при переименовании самого заголовка. На
  MkDocs это делала настройка `slugify: pymdownx.slugs.slugify`. После перехода на Sphinx (P1) —
  небольшое преобразование `_unicode_section_ids` в `docs/conf.py`: Sphinx, как и docutils, иначе
  нумерует разделы `#id1`, `#id2`. Адреса якорей при переезде сохранились.
- Для разделов, на которые ссылаются извне, задан явный якорь, который не зависит даже от текста
  заголовка: метка MyST `(strategy2)=` перед разделом «Стратегия 2» в T2.
- Страница T1 переехала с `/theory/` на `/t1/`, чтобы адреса были единообразными. Старый адрес
  сохранён страницей-переадресацией, якорь при этом переносится.

**Переадресация** без доступа к серверу возможна только средствами HTML: `<meta http-equiv="refresh">`
и `<link rel="canonical">`. HTTP 301, который понимают все поисковики и клиенты, на Helios
недоступен (см. ниже). Плагин `mkdocs-redirects` генерирует такие же HTML-страницы, но его
текущая версия 1.2.3 тянет за собой `properdocs` — **вторую копию MkDocs** (форк 1.x, появившийся
после раскола вокруг MkDocs 2.0). Ради одной переадресации это неоправданная зависимость, поэтому
страница [`docs/_extra/theory/index.html`](https://github.com/crasavella04/python-lab3/blob/main/docs/_extra/theory/index.html)
написана вручную (Sphinx копирует её как есть через `html_extra_path`), а `check_site.py` после каждого деплоя проверяет, что старый адрес переадресует
на новый.

## Версии сайта, кода и данных

Публикация должна отвечать на вопрос «из какого кода и каких данных получена эта цифра».
На этом сайте три уровня связи:

1. **Страница → коммит.** В подвале каждой страницы — ссылка «Сборка `abc1234`» на дерево
   репозитория в этом коммите. Тот же коммит записан в `<meta name="build-marker">`, и CI сверяет
   его после деплоя.
2. **Результат → код, параметры, данные.** У результатов T2 есть `manifest.json` с хешами кода,
   параметров, датасета и самих файлов результатов. CI не опубликует результат, расходящийся с
   кодом.
3. **Датасет → версия.** Паспорт `DATASET.json`: версия, SHA-256, источник, лицензия.

**Несколько версий сайта одновременно** (`/v1/`, `/v2/`, `latest`) обычно делают плагинами `mike`
(MkDocs) и `sphinx-multiversion` (Sphinx). У Pelican и Jupyter Book таких средств нет. `mike`
устроен так: каждую версию он коммитит в ветку `gh-pages`. Значит, workflow нужен
`contents: write`, и это противоречит модели деплоя из T4, где у job нет права записи в
репозиторий. Для этого сайта версии фиксируются иначе: **GitHub Release + Zenodo**. Каждый
релиз получает свой DOI и неизменяемый архив, а сайт показывает последнюю версию.

**Даты в sitemap.** MkDocs ставит каждой странице `<lastmod>` с датой сборки: пересобрали сайт —
поисковик видит, что изменились все страницы. После перехода на Sphinx эта проблема решилась
плагином `sphinx-sitemap`: через зависимость `sphinx-last-updated-by-git` он берёт дату последнего
коммита каждой страницы. Условие — полная история Git в CI (`fetch-depth: 0`); та же дата
выводится в подвале страницы.

## DOI и ORCID

**DOI** — постоянный идентификатор, который разрешается через `doi.org` даже при смене адреса
сайта. Путь для GitHub-репозитория — интеграция с **Zenodo**:

1. Войти в Zenodo через GitHub и включить репозиторий в разделе GitHub.
2. Выпустить на GitHub релиз (например, `v1.0`).
3. Zenodo архивирует состояние репозитория на момент релиза и выдаёт два DOI:
   - **concept DOI** — указывает на последнюю версию, его и стоит приводить в ссылках;
   - **version DOI** — на конкретный релиз, для точного воспроизведения.
4. Вписать DOI в `docs/conf.py` (`html_context.citation.doi`) и в `CITATION.cff`. После этого он появится в
   метаданных всех страниц-публикаций и в подвале.

Метаданные архива Zenodo берёт из
[`.zenodo.json`](https://github.com/crasavella04/python-lab3/blob/main/.zenodo.json): тип —
отчёт, лицензия, связь с сайтом и репозиторием. Файл
[`CITATION.cff`](https://github.com/crasavella04/python-lab3/blob/main/CITATION.cff) прошёл проверку
валидатором `cffconvert` по схеме 1.2.0. По нему GitHub показывает кнопку «Cite this repository»
с готовой ссылкой в APA и BibTeX.

**ORCID** однозначно связывает публикацию с автором, даже если автор меняет фамилию или пишет её
латиницей по-разному. В метаданных он передаётся как `citation_author_orcid` и как `@id` автора
в JSON-LD. Шаблон сайта это поддерживает, нужен только идентификатор автора.

## Метаданные для индексации

Что выводит в HTML каждый генератор, если передать ему автора, описание, адрес сайта, DOI и
лицензию родными средствами:

| | MkDocs Material | Sphinx + MyST | Pelican | Jupyter Book 2 |
|---|---|---|---|---|
| `<meta name="description">` | ✔ | — | ✔ | ✔ |
| `<meta name="author">` | ✔ | — | — | — |
| `rel="canonical"` | ✔ | ✔ | — | — |
| Open Graph | — | — | — | ✔ `og:title`, `og:description`, `og:image` |
| Highwire Press (`citation_*`) | — | — | — | — |
| Dublin Core | — | — | — | — |
| JSON-LD | — | — | — | — |
| ORCID и DOI на странице | — | — | — | ✔ видимым текстом и ссылкой |
| `sitemap.xml` | ✔ | — | — | ✔ |
| `robots.txt` | — | — | — | ✔ |

Ни один генератор не выводит теги **Google Scholar (Highwire Press)**, **Dublin Core** и
**JSON-LD**. Дальше всех заходит Jupyter Book, но и у него нашлись две ошибки:
- в `sitemap.xml` все 102 адреса имеют вид `http://localhost:3000/...` (адрес временного сервера
  сборки), и `robots.txt` указывает туда же. Если не задать адрес сайта при сборке, поисковик
  получит ссылки на чужой локальный сервер;
- `og:image` — относительный путь `/build/response-….svg`, хотя протокол Open Graph требует
  абсолютный URL.

### Что сделано на этом сайте

Шаблон [`docs/_templates/metadata.html`](https://github.com/crasavella04/python-lab3/blob/main/docs/_templates/metadata.html)
берёт данные из `docs/conf.py` (`html_context.citation`) и из front matter страницы и выводит.
Сначала он был сделан для MkDocs и при переходе на Sphinx (P1) перенесён почти без изменений:
поменялись только имена переменных шаблона (`page.meta` → `meta`, `page.canonical_url` → `pageurl`).

| Для каких страниц | Что | Зачем |
|---|---|---|
| все | `rel="license"`, Open Graph (`og:type`, `og:title`, `og:description`, `og:url`, `og:locale`) | машиночитаемая лицензия; превью ссылки в мессенджерах |
| исследования T1–T5 (в front matter есть `date`) | Highwire Press: `citation_title`, `citation_author`, `citation_author_orcid`, `citation_publication_date` (`ГГГГ/ММ/ДД`), `citation_technical_report_institution`, `citation_abstract_html_url`, `citation_doi` | индексация в Google Scholar |
| то же | Dublin Core: `DC.title`, `DC.creator`, `DC.date`, `DC.rights`, `DC.identifier`… | библиотечные и репозиторные системы |
| то же | JSON-LD `ScholarlyArticle`: авторы, дата, лицензия, `isBasedOn` — ссылка на коммит | структурированные данные для поисковиков |
| T2 | вложенный `Dataset`: описание, переменные, лицензия CC0, ссылка на `coverage.csv` | Google Dataset Search |

`citation_title` берётся из полного заголовка страницы, а не из короткой подписи в меню: для
цитирования нужно «T2. Конвейер „эксперимент → артефакт → страница“», а не «T2. Конвейер
вычислений».

## Лицензирование текста, кода и данных

Текст, код и данные лицензируются раздельно — подробно на странице [«Лицензии»](license.md):

| Что | Лицензия | Где указано машиночитаемо |
|---|---|---|
| Текст | CC BY 4.0 | `rel="license"`, `DC.rights`, `license` в JSON-LD |
| Код | MIT | `LICENSE`, `CITATION.cff` |
| Данные T2 | CC0 1.0 | `DATASET.json` (`license`), `license` у `Dataset` в JSON-LD |

Данные получили CC0, а не CC BY. Набор чисел — не творческое произведение, а обязательное указание
авторства мешает включать данные в другие наборы. Ссылаться на источник всё равно принято, но
это норма науки, а не условие лицензии.

## FAIR

| Принцип | Требование | На этом сайте | Статус |
|---|---|---|---|
| **F1** | глобальный постоянный идентификатор | URL сайта не постоянный; DOI — после релиза в Zenodo | после DOI |
| **F2** | богатые метаданные | Highwire, Dublin Core, JSON-LD, Open Graph | ✔ |
| **F3** | метаданные содержат идентификатор данных | `citation_doi`, `identifier` в JSON-LD — после DOI; сейчас URL | после DOI |
| **F4** | регистрация в поисковых ресурсах | `sitemap.xml`; Zenodo индексируется сам; Google Search Console — вручную | частично |
| **A1** | доступ по открытому стандартному протоколу | HTTPS, без авторизации | ✔ |
| **A2** | метаданные доступны, даже если данных уже нет | Zenodo хранит запись бессрочно; сайт на Helios — нет | после DOI |
| **I1** | формальный язык представления | JSON-LD schema.org, CSV, JSON-манифест | ✔ |
| **I2** | словари, сами следующие FAIR | schema.org, Dublin Core, SPDX-идентификаторы лицензий | ✔ |
| **I3** | ссылки на другие объекты | `isBasedOn` на коммит, `related_identifiers` в Zenodo | ✔ |
| **R1.1** | ясная лицензия | раздельные лицензии, машиночитаемо | ✔ |
| **R1.2** | происхождение (provenance) | `manifest.json` T2, коммит в подвале и `build-marker` | ✔ |
| **R1.3** | стандарты сообщества | `CITATION.cff`, CSV, schema.org `Dataset` | ✔ |

Главное, чего не хватает до полной FAIR-публикации, — **постоянный идентификатор**. Его даёт не
сайт, а архив: сайт остаётся удобной витриной, а ссылаться нужно на DOI.

## Что достижимо на Helios

| Механизм | На Helios | Почему |
|---|---|---|
| Метатеги Highwire, Dublin Core, Open Graph, JSON-LD | ✔ | они внутри HTML и от сервера не зависят |
| `sitemap.xml` с правильными адресами | ✔ | генератор собирает его под адрес Helios (`SITE_URL` в CI); проверено: адреса вида `https://se.ifmo.ru/~s564180/python-lab3/…` |
| `robots.txt` | ✘ | поисковики читают его **только из корня хоста**. `se.ifmo.ru/robots.txt` принадлежит университету: он разрешает всё и указывает на sitemap университета, а не на наш. Наш `robots.txt` в подкаталоге никто не прочтёт. Остаётся отправить sitemap вручную, например в Google Search Console как ресурс с префиксом URL |
| HTTP 301 при переименовании | ✘ | для этого нужен `.htaccess` с `Redirect` или настройки сервера, а `.htaccess` на Helios отклоняется с ошибкой 500 (см. «Отладка»). Работает только переадресация через HTML, как сделано для `/theory/` |
| Свои HTTP-заголовки (`Link: rel="cite-as"`, `X-Robots-Tag`, CORS для данных) | ✘ | по той же причине; сервер отдаёт только `Server: nginx` |
| **Постоянный адрес** | ✘ | адрес привязан к учётной записи студента `~s564180`. После выпуска учётную запись удалят, и все ссылки на сайт сломаются. Своего домена на Helios не подключить |
| HTTPS | ✔ | сертификат университета на `se.ifmo.ru` |
| Несколько версий сайта | ✔, вручную | можно выкладывать версии в подкаталоги `public_html/python-lab3/v1/`; скрипт деплоя (T4) пришлось бы расширить |
| DOI | ✔, но **не на Helios** | DOI выдаёт Zenodo, и указывать он должен на архив Zenodo, а не на сайт: адрес на Helios временный |

Итог: на Helios достижимо всё, что живёт **внутри файлов**: метаданные, sitemap, переадресация
через HTML, версии в подкаталогах. Недостижимо всё, что требует **управления хостом**: свой
`robots.txt`, HTTP-заголовки и редиректы, постоянный адрес. Поэтому Helios годится как витрина
результатов на время обучения, а постоянная ссылка для цитирования — это DOI архива в Zenodo. На
GitHub Pages часть ограничений снимается: можно подключить свой домен, и тогда корневой
`robots.txt` становится нашим. HTTP-заголовки и 301 там тоже недоступны.
